Block 1: Daten laden

Worum es geht: In Deinem Vorprojekt lagen alle Daten direkt im Code (Listen.js). Hier kommen sie von außen, von einem Server. Dafür braucht es vier neue Konzepte. Wir verfolgen dazu einen Weg durch vier Dateien: Was passiert, wenn Du /jobs/8 öffnest?

JobDetail.jsx  →  useAsync.js  →  api/index.js  →  mock.js  (später: http.js → Server)
   Seite          wartet und        entscheidet,      liefert
                  merkt sich        woher die         die Daten
                  den Zustand       Daten kommen
1. Die Seite: drei Zustände

Datei: src/pages/JobDetail.jsx

jsx
const { id } = useParams();
const { data, error, loading } = useAsync(() => getJob(id), [id]);
if (loading) return <Loading />;
if (error) return <ErrorState error={error} />;
const { job } = data;

Konzept: Daten von außen sind nicht sofort da, und sie können fehlschlagen. Deshalb kennt jede Seite, die Daten lädt, drei Zustände:

Zustand	Bedeutung	Anzeige
loading	Anfrage läuft noch	Lade-Kreisel
error	Anfrage ist fehlgeschlagen (z. B. Stelle gibt es nicht)	Fehlerseite
data	Antwort ist da	die eigentliche Seite

Die frühen return-Zeilen sorgen dafür, dass der Rest der Funktion nur läuft, wenn data wirklich existiert. Ohne sie würde data.job beim ersten Rendern abstürzen, weil data da noch null ist.

Die Seite selbst weiß nicht, wie geladen wird. Sie sagt nur: „Lade mir getJob(id).“ Den Rest erledigt useAsync.

2. Der Hook: warten, ohne einzufrieren

Datei: src/hooks/useAsync.js

js
export function useAsync(fn, deps = []) {
  const [state, setState] = useState({ data: null, error: null, loading: true });
  const run = useCallback(fn, deps);

  const reload = useCallback(async () => {
    setState((s) => ({ ...s, loading: true }));
    try {
      const data = await run();
      setState({ data, error: null, loading: false });
    } catch (error) {
      setState({ data: null, error, loading: false });
    }
  }, [run]);

  useEffect(() => { reload(); }, [reload]);

  return { ...state, reload };
}

Konzept 1: Eigener Hook. Ein Hook ist eine Funktion, die mit use beginnt und selbst Hooks wie useState benutzt. Hier steckt die Lade-Logik einmal drin, und jede Seite nutzt sie. Ohne den Hook stünde derselbe Code in 13 Seiten.

Konzept 2: async / await und Promises. Eine Anfrage an einen Server dauert. JavaScript darf in der Zeit nicht stehen bleiben, sonst friert die Seite ein. Deshalb gibt run() sofort ein Promise zurück, ein Versprechen auf ein späteres Ergebnis. Vergleich: die Abholnummer beim Bäcker.

await run() heißt: „Warte hier auf das Ergebnis.“ Nur diese Funktion pausiert, die Seite bleibt bedienbar.
await geht nur in Funktionen, die mit async markiert sind.

Konzept 3: try / catch. Geht beim Warten etwas schief, etwa weil der Server mit 404 antwortet oder nicht erreichbar ist, springt JavaScript aus dem try-Block direkt in den catch-Block. So landet entweder data oder error im State, nie beides.

Konzept 4: useEffect. Code, der nach dem Zeichnen der Seite laufen soll. Das Laden darf nicht direkt im Komponentenkörper stehen: Dann würde es bei jedem Rendern neu starten, das Ergebnis würde den State ändern, das löst wieder ein Rendern aus, und so weiter, endlos. useEffect startet das Laden einmal und dann nur wieder, wenn sich ein Wert im Array ändert. Bei der Detailseite ist das die id.

Der zeitliche Ablauf beim Öffnen von /jobs/8:

React zeichnet die Seite mit loading: true → Kreisel
useEffect startet reload() → Anfrage geht los
… warten …
Antwort kommt → setState({ data })
React zeichnet neu → Seite mit Inhalt

useCallback musst Du nicht selbst schreiben können. Es sorgt nur dafür, dass reload nicht bei jedem Rendern als „neue“ Funktion gilt. Sonst würde useEffect in einer Endlosschleife neu laden.

reload wird mit zurückgegeben. Seiten, die etwas ändern, zum Beispiel einen Status setzen, rufen danach reload() auf und holen sich den neuen Stand vom Server.

3. Die API-Schicht: woher kommen die Daten?

Datei: src/api/index.js

js
export function getJob(id) {
  return mock.getJob(id);
  // return request('GET', `/jobs/${id}`);
}

Konzept: alle Server-Anfragen an einer Stelle. Keine Seite ruft selbst fetch auf. Sie rufen nur Funktionen aus dieser Datei auf: getJob, getJobs, applyToJob usw. Das bringt zwei Vorteile:

Austauschbar: Heute antwortet der Mock, später Dein Server. Umgestellt wird nur hier, eine Zeile pro Funktion. Die Seiten merken nichts.
Übersicht: Diese Datei ist gleichzeitig die Liste aller Endpunkte, die Dein Backend später können muss. Die genaue Beschreibung steht in API.md.
4a. Der Mock: ein nachgebauter Server

Datei: src/api/mock.js

js
export const getJob = (id) => respond((db) => {
  const job = db.jobs.find((j) => j.id === Number(id) && j.status === 'published');
  if (!job) throw new ApiError(404, { error: 'Diese Stelle ist nicht (mehr) ausgeschrieben.' });
  return { job };
});

Konzept: Der Mock tut so, als wäre er ein Server. Er speichert Daten im Browser (localStorage) und respond() wartet künstlich 250 ms, wie eine echte Netzwerkanfrage. Er antwortet mit genau denselben Daten und Fehlern, die Dein Backend später liefern soll. So konnte das Frontend fertig werden, bevor es ein Backend gibt. Am Ende wird diese Datei gelöscht.

4b. Der echte Weg: fetch

Datei: src/api/http.js, wird ab dem Backend benutzt:

js
export async function request(method, path, { body, formData } = {}) {
  ...
  res = await fetch(`/api${path}`, { method, headers, body: payload, credentials: 'same-origin' });
  ...
  const data = await res.json().catch(() => ({}));
  if (!res.ok) throw new ApiError(res.status, data);
  return data;
}

Konzept: fetch und JSON.

fetch(adresse, optionen) ist die eingebaute Browser-Funktion, um eine HTTP-Anfrage zu schicken. Sie gibt ein Promise zurück, deshalb await.
Der Server antwortet mit Text im JSON-Format, zum Beispiel {"job":{"id":8,"title":"…"}}. res.json() macht daraus ein JavaScript-Objekt.
res.ok ist true bei Statuscode 200–299. Bei allem anderen (404, 422, 500 …) wirft die Funktion einen ApiError. Der landet im catch von useAsync, und die Seite zeigt die Fehlerseite.
Zusammenfassung Block 1
Konzept	In einem Satz	Datei
Drei Zustände	lädt / Fehler / Daten, jede Seite muss alle drei können	JobDetail.jsx
Eigener Hook	Lade-Logik einmal schreiben, überall nutzen	useAsync.js
Promise, async/await	auf ein Ergebnis warten, ohne die Seite einzufrieren	useAsync.js, http.js
try/catch	Fehler beim Warten abfangen	useAsync.js
useEffect	Laden starten, nachdem die Seite gezeichnet ist	useAsync.js
API-Schicht	alle Anfragen an einer Stelle, Mock oder Server austauschbar	api/index.js
fetch und JSON	HTTP-Anfrage schicken, Antwort in ein Objekt umwandeln	http.js

Wenn etwas unklar ist, frag. Sonst schreib „weiter“, dann kommt Block 2: Router, also wie mehrere Seiten mit eigener Adresse funktionieren.

# Automatische Tests: das Konzept in Stichpunkten

## Die drei Bausteine

**1. Testdatei: `server/test/apply.test.js`**
- Beschreibt die Testfälle: was an den Server geschickt wird und was zurückkommen muss.
- `test('T01: …', …)` ist ein Testfall.
- `assert.equal(a, b)` prüft „a muss gleich b sein“, sonst fällt der Test durch.
- Der Name endet auf `.test.js`, daran erkennt Node die Datei als Test.

**2. Befehl festlegen: `server/package.json`**
- `"test": "node --test"` macht `npm test` zur Abkürzung für `node --test`.
- Der Dateiname steht dort nicht. Node sucht selbst alle `*.test.js`-Dateien.
- Neue Testdateien laufen deshalb automatisch mit.

**3. Ausführen im Terminal**
- Im Ordner `server` den Befehl `npm test` eingeben.
- Jeder Test zeigt ✔ oder ✖, am Ende stehen die Zahlen: `tests`, `pass`, `fail`.

## Was beim Ausführen passiert

1. Die Testumgebung wird eingestellt: Datenbank nur im Arbeitsspeicher (`:memory:`), PDFs in einen Temp-Ordner.
2. `init-db.js` legt in der Test-Datenbank die Tabellen und Stellen an.
3. `before` startet einen eigenen Test-Server auf einem freien Port.
4. `beforeEach` leert vor jedem Test die Bewerbungsdaten, damit jeder Test frisch startet.
5. Jeder Test schickt eine Bewerbung über HTTP und prüft Statuscode, Antwort und Datenbank.
6. `after` stoppt den Server und löscht den Temp-Ordner.
7. Die echte Datenbank und die echten Uploads bleiben unberührt.

Erklärungen:
- Hash: eine Einbahnstraße. Aus dem Passwort wird ein Wert berechnet, aber aus dem Wert lässt sich
  das Passwort nicht zurückrechnen. Wird die Datenbank gestohlen, hat der Angreifer keine Passwörter.
- scrypt: Hash-Verfahren, das in Node eingebaut ist (kein Zusatzpaket, E8) und von der OWASP
  empfohlen wird. scrypt ist absichtlich langsam und braucht viel Arbeitsspeicher. Für einen Login
  merkt man das kaum, aber wer Millionen Passwörter durchprobieren will, braucht sehr lange.
  Einstellungen nach OWASP: N=2^17, r=8, p=1.
- Salt: ein Zufallswert pro Passwort, der mit in den Hash eingerechnet und mit gespeichert wird.
  Zwei Nutzer mit demselben Passwort haben dadurch verschiedene Hashes, und vorberechnete
  Tabellen mit Hashes bekannter Passwörter (Rainbow Tables) nützen nichts.
- timingSafeEqual: vergleicht zwei Werte immer gleich schnell. Ein normaler Vergleich bricht beim
  ersten Unterschied ab; an der Antwortzeit könnte ein Angreifer ablesen, wie viel schon stimmt.
- promisify/await: scrypt läuft im Hintergrund, damit der Server währenddessen andere Anfragen
  bearbeiten kann und nicht blockiert.
- .env: Datei für Werte, die sich je nach Rechner unterscheiden oder geheim sind (Passwörter).
  Sie gehört nicht in den Code und nicht ins Repository. Die .env.example zeigt anderen,
  welche Einträge sie brauchen.
- --env-file: in Node eingebaut, lädt die .env. Das Zusatzpaket dotenv ist dadurch nicht nötig (E8).
- Prüfung VOR dem Löschen: init-db löscht zuerst alle Tabellen. Würde die Passwortprüfung erst
  danach kommen, stünde man bei einem Fehler mit einer leeren Datenbank da.
- Tests mit eigenen Zugangsdaten: So laufen sie auf jedem Rechner, auch ohne .env,

B6 Etappe 2: Login und Sitzung

Ziel:
Recruiter und Admins melden sich mit E-Mail und Passwort an. Der Server merkt sich die Anmeldung
als Sitzung und erkennt den Nutzer bei jeder weiteren Anfrage am Cookie. Abmelden beendet die Sitzung.
Grundlage: E7 (Sitzung statt JWT, Cookie-Einstellungen, Zeitgrenzen), E8 (keine Zusatzpakete).

So funktioniert eine Sitzung:
1. Beim Login erzeugt der Server einen langen Zufallswert und schickt ihn als Cookie an den Browser.
2. Der Browser schickt den Cookie automatisch bei jeder Anfrage an dieselbe Seite mit.
3. Der Server sucht in der Tabelle sessions, zu welchem Nutzer der Wert gehört und ob er noch gilt.
4. Beim Logout oder bei Ablauf wird der Eintrag gelöscht. Der Cookie ist danach wertlos.
Unterschied zu JWT: Bei JWT steht alles im Token selbst, der Server speichert nichts und kann
ein ausgegebenes Token vor Ablauf nicht zurückziehen. Bei Sitzungen kann der Server jederzeit
beenden (Logout, Sperre eines Nutzers). Deshalb Sitzungen (E7).

Gebaut:
1. Tabelle sessions in init-db.js (id, user_id, created_at, last_seen_at).
   - technische Tabelle, nicht im ER-Diagramm aus E2 (im Bericht ein Satz dazu)
   - DROP vor users, weil sessions auf users verweist
   - ON DELETE CASCADE: Wird ein Nutzer gelöscht, verschwinden seine Sitzungen mit
2. server/lib/session.js:
   - createSession: Zufallswert erzeugen, Hash davon speichern, Wert zurückgeben
   - getSessionUser: Nutzer zum Cookie finden, Ablauf prüfen, Aktivität merken
   - deleteSession: Sitzung löschen
   - readSessionCookie: Cookie "sid" aus dem Anfrage-Header lesen
   - cookieOptions: Einstellungen für den Cookie
3. server/routes/auth.js:
   - POST /api/login, POST /api/logout, GET /api/session
4. app.js: auth-Routen unter /api eingehängt.
5. Frontend src/api/index.js: getSession, login, logout vom Mock auf den Server umgestellt.
6. Login.jsx: grauen Kasten "Demo-Zugänge (Mock)" entfernt.

Erklärungen:
- In sessions steht nur der Hash des Cookie-Werts (SHA-256), nicht der Wert selbst.
  Gleiches Prinzip wie beim Passwort: Wer die Datenbank stiehlt, kann sich damit nicht anmelden.
- Cookie-Einstellungen (E7):
  - HttpOnly: JavaScript im Browser kann den Cookie nicht lesen. Eingeschleuster Schadcode (XSS)
    kann ihn also nicht stehlen.
  - SameSite=Strict: Der Browser schickt den Cookie nur bei Anfragen von der eigenen Seite.
    Eine fremde Seite kann keine Aktionen im Namen des angemeldeten Nutzers auslösen.
  - Secure: Cookie nur über HTTPS. Nur im Betrieb aktiv (NODE_ENV=production),
    weil localhost kein HTTPS hat. Bewusste Entscheidung, im Bericht offen benennen.
- Zeitgrenzen (E7): Sitzung endet nach 30 Minuten ohne Aktivität oder spätestens nach 8 Stunden.
  Jede Anfrage setzt die 30 Minuten zurück (last_seen_at). Gesperrte Nutzer verlieren ihre Sitzung.
- Cookie-Lesen ohne cookie-parser: Der Browser schickt alle Cookies in einer Zeile
  ("sid=abc; theme=dark"). Die Funktion sucht "sid" heraus. Kein Zusatzpaket nötig (E8).
- Gleiche Fehlermeldung bei falscher E-Mail und falschem Passwort: Sonst könnte ein Angreifer
  herausfinden, welche E-Mail-Adressen ein Konto haben (OWASP Authentication Cheat Sheet).
- Dummy-Hash: Auch bei unbekannter E-Mail wird ein Passwort-Hash berechnet. Sonst wäre die
  Antwort bei unbekannten E-Mails spürbar schneller und würde dasselbe verraten.
- Jeder Login erzeugt eine neue Sitzung mit neuem Zufallswert. Ein alter, vielleicht
  abgefangener Wert ist damit nicht weiterverwendbar.

B6 Etappe 3: Login-Sperre nach Fehlversuchen

Ziel:
Nach 5 falschen Versuchen ist eine E-Mail-Adresse 15 Minuten gesperrt. In dieser Zeit antwortet
der Server mit 429, auch wenn das Passwort stimmt.
Grundlage: E7 (Schutz gegen Durchprobieren von Passwörtern, OWASP).

Gebaut:
1. Tabelle login_attempts in init-db.js (email, failed, locked_until).
   - technische Tabelle wie sessions, nicht im ER-Diagramm
2. server/lib/login-lock.js mit drei Funktionen:
   - lockedMinutes(email): Ist die E-Mail gesperrt? Gibt die Restminuten zurück, sonst 0.
   - recordFailure(email): Fehlversuch zählen, beim 5. Versuch die Sperre setzen.
   - clearFailures(email): bei erfolgreichem Login den Zähler löschen.
3. routes/auth.js, Login-Route:
   - ganz am Anfang Sperre prüfen -> 429 mit Restminuten
   - bei falschem Login recordFailure
   - bei richtigem Login clearFailures

Erklärungen:
- Gezählt wird pro E-Mail-Adresse, nicht pro Nutzer-ID. So werden auch Versuche mit nicht
  vorhandenen E-Mails gezählt und gesperrt. Würden nur echte Konten gesperrt, könnte ein Angreifer
  an der 429 erkennen, welche E-Mails ein Konto haben. Gleicher Gedanke wie bei der einheitlichen
  Fehlermeldung in Etappe 2. Deshalb auch eine eigene Tabelle statt Spalten in users.
- Die Sperre wird VOR der Passwortprüfung geprüft. Während der Sperre hilft auch das richtige
  Passwort nicht. Sonst könnte ein Angreifer einfach weiterprobieren, und die Sperre wäre wirkungslos.
- 429 = "Too Many Requests", der passende Statuscode für zu viele Versuche.
  Das Frontend zeigt die Meldung des Servers bereits an.
- Der 5. Fehlversuch bekommt noch 401 (und setzt die Sperre), der 6. dann 429.
  Passt zum Sicherheitstest aus E9: "sechs falsche Passwörter hintereinander (429)".
- Nach Ablauf einer Sperre wird wieder bei 0 gezählt. Sonst wäre man nach einer abgelaufenen
  Sperre schon beim nächsten Tippfehler wieder gesperrt.
- Erfolgreicher Login löscht den Zähler: Zwei Tippfehler gestern zählen heute nicht mit.
- INSERT ... ON CONFLICT ... DO UPDATE: Gibt es für die E-Mail noch keine Zeile, wird eine angelegt,
  sonst aktualisiert. Eine Abfrage für beide Fälle.
- Math.ceil(ms / 60000): rechnet Millisekunden in aufgerundete Minuten um, für die Meldung.

Fehler und Lösung:
- Den if-Block in auth.js zusätzlich statt ersetzend eingefügt -> doppelte return,
  doppelte Variablen (passwordOk, token) -> 4 Probleme, Server startete nicht
  ("Failed running 'index.js'").
- Neue Datei falsch benannt: login-block.js statt login-lock.js -> Import findet die Datei nicht.
- Lösung: auth.js komplett durch die saubere Fassung ersetzt, Datei umbenannt.
- Erkenntnis: Vor dem Starten die Anzeige "Problems" unten links prüfen. Sie muss 0 sein.
  Bei vielen kleinen Fehlern in einer Datei ist komplettes Ersetzen sicherer als Flicken.

Getestet:
- Versuch 1-5 -> "E-Mail-Adresse oder Passwort ist falsch."
- Versuch 6 -> "Zu viele Fehlversuche. Bitte versuche es in 15 Minuten erneut."
- richtiges Passwort während der Sperre -> weiterhin gesperrt
- Sperre aufgehoben mit: sqlite3 data/ats.db "DELETE FROM login_attempts;"
- danach Login erfolgreich
- npm test: 8 von 8 grün

Ziel:

  - mit gültiger Sitzung: legt den Nutzer in req.user ab und ruft next() auf = "weiter zur Route"
- req.user: Die Routen wissen dadurch, WER die Anfrage stellt. Wird in B7 gebraucht:
  Stellen bearbeiten nur Ersteller oder Admin, Autor einer Notiz, Löschen nur Admin (E3).
- router.use(requireLogin) ganz oben in admin.js: Der Wächter gilt für ALLE Routen dieser Datei,
  auch für die, die in B7 dazukommen. Keine Route kann aus Versehen ungeschützt bleiben.
  Sicherer, als den Login in jeder Route einzeln zu prüfen (OWASP A01: Broken Access Control).

  "/dashboard" wird zu "/api/admin/dashboard".

    Löschungen in den nächsten 30 Tagen (delete_after, E5)
  - counts: GROUP BY status zählt je Stufe; über STAGES.map erscheinen auch Stufen mit 0,
    in der richtigen Reihenfolge
  - recent: die 5 neuesten Bewerbungen
- Anonymität (E4): Solange revealed_at leer ist, steht dort nur "Bewerbung #0001", kein Name.

  padStart(4, '0') macht aus 1 die Nummer 0001.
- Datensparsamkeit (E5): Ausgeliefert werden nur die Felder, die das Dashboard anzeigt,
  keine E-Mail, kein Anschreiben.

- In der curl-Antwort steht "X-Powered-By: Express". Damit verrät der Server seine Technik,
  das erleichtert Angreifern die Suche nach bekannten Lücken. Helmet entfernt diese Zeile in B8.
  Screenshot als Vorher/Nachher für den Bericht gemacht.

Übergangszustand (verstanden):
- Stellen, Bewerbungen, Pipeline und Nutzer:innen zeigen noch "401 Bitte melde Dich an",
  weil sie noch am Mock hängen. Wird in B7 umgestellt.

B6 Etappe 5: Automatische Tests für Login und Schutz

Ziel:
Alles, was in B6 von Hand geprüft wurde (Login, Logout, Sperre, Schutz des Verwaltungsbereichs),
läuft jetzt automatisch per "npm test". Damit ist auch T07 aus den Top 10 des Testplans (E9) abgedeckt.

Gebaut:
- Neue Testdatei server/test/auth.test.js.
  Der Aufbau ist derselbe wie in apply.test.js und status.test.js: Datenbank nur im Arbeitsspeicher
  (:memory:), eigene Test-Zugangsdaten für den Admin, eigener Test-Server auf einem freien Port.
  Die echte Datenbank und die echte .env werden nicht angefasst.
- node --test findet die neue Datei automatisch, weil sie auf .test.js endet.
  package.json musste nicht geändert werden.

Neu in diesen Tests: Cookie von Hand weiterreichen
- Im Browser schickt der Browser den Sitzungs-Cookie automatisch bei jeder Anfrage mit.
  Im Test gibt es keinen Browser, deshalb macht der Test das selbst:
  1. Nach dem Login den Cookie aus der Antwort lesen (Header "set-cookie").
  2. Davon nur den Teil "sid=..." nehmen (alles vor dem ersten Semikolon).
     Der Rest sind Einstellungen wie HttpOnly oder Max-Age, die nur der Browser braucht.
  3. Bei der nächsten Anfrage als Header "Cookie" mitschicken.
- So lässt sich prüfen, ob der Server die Sitzung erkennt (Dashboard 200)
  und ob sie nach dem Logout ungültig ist (Dashboard 401).

Unabhängigkeit der Tests:
- beforeEach leert vor jedem Test zusätzlich die Tabellen sessions und login_attempts.
- Warum: Test A04 sperrt das Admin-Konto absichtlich. Ohne das Leeren wäre der Admin im nächsten
  Test noch gesperrt, und der Test würde aus dem falschen Grund fehlschlagen.
  Jeder Test muss für sich allein funktionieren, egal in welcher Reihenfolge
  (Skript Qualitätssicherung, Kap. 6.2, S. 101: Unabhängigkeit).

Testfälle und was sie absichern:
- T07 (Top 10 aus E9): Verwaltungsroute ohne Login -> 401.
  Sichert: Der Wächter requireLogin schützt den Verwaltungsbereich (E3, OWASP A01).
- A01: falsches Passwort und unbekannte E-Mail -> beide 401 mit exakt gleicher Antwort (deepEqual).
  Sichert: Ein Angreifer kann nicht herausfinden, welche E-Mail-Adressen ein Konto haben.
- A02: richtiger Login -> 200, Cookie enthält HttpOnly und SameSite=Strict, Dashboard erreichbar.
  Sichert: die Cookie-Einstellungen aus E7. Würde später jemand HttpOnly aus Versehen entfernen,
  schlägt der Test sofort fehl (Regressionsfähigkeit).
- A03: nach dem Logout mit dem alten Cookie -> 401.
  Sichert: Abmelden beendet die Sitzung wirklich auf dem Server, nicht nur im Browser.
  Das ist der Vorteil von Sitzungen gegenüber JWT (E7).
- A04: fünfmal falsches Passwort -> 401, sechster Versuch -> 429,
  danach auch mit richtigem Passwort -> 429.
  Sichert: die Login-Sperre aus E7 (5 Fehlversuche -> 15 Minuten). Entspricht dem
  Sicherheitstest "sechs falsche Passwörter hintereinander" aus E9.
- A05: nach einer neuen Bewerbung zeigt das Dashboard "Bewerbung #0001",
  der Nachname kommt in der Antwort nicht vor.
  Sichert: die anonyme Vorauswahl aus E4 und die Datensparsamkeit aus E5.

Beobachtung:
- Die Tests dauern jetzt einige Sekunden statt unter einer Sekunde.
  Grund: Jeder Login berechnet einen scrypt-Hash, und scrypt ist absichtlich langsam und
  speicherhungrig, damit massenhaftes Durchprobieren von Passwörtern teuer wird.
  Rund 12 Logins in den Tests summieren sich. Das ist gewollt und kein Fehler.

Ergebnis: 14 von 14 Tests bestanden
(T01-T03, T07, A01-A05, S01-S04).

Begriffe:
- Testfall-IDs: T = Top 10 aus E9, A = Anmeldung, S = Statusseite.
  A- und S-Fälle gehören laut E9 in den Anhang des Berichts.
- deepEqual: vergleicht zwei Objekte Feld für Feld, nicht nur, ob es dasselbe Objekt ist.
- Regressionsfähigkeit: Nach jeder Änderung zeigt npm test, ob etwas Bestehendes kaputtgegangen ist.

B7 Etappe 2: Bewerbungsliste, Detail und PDF-Download angeschlossen

Ziel:
Die Seite "Bewerbungen" (Liste, Detail) und der Lebenslauf-Download laufen über den Server.
Umgesetzt mit den Entscheidungen aus E3, E4 und der neuen Abwägung zur Anonymität:
- alle Recruiter sehen alle Bewerbungen (E3)
- anonym bis zum bestätigten Aufdecken (E4)
- Suche: Nummer immer, Name/E-Mail nur bei aufgedeckten Bewerbungen (neu entschieden)
- PDF auch anonym herunterladbar, mit Hinweis; Hinweis im Bewerbungsformular (neu entschieden, Variante A)

Neue Entscheidungen (Lücken im Konzept E4 erkannt):
1. Lebenslauf und Anonymität:
   Im PDF stehen meist Name und Kontaktdaten, Öffnen hebt die Anonymität faktisch auf.
   Der Lebenslauf ist für die Bewertung aber zwingend nötig.
   Erkenntnis: Für die Zuordnung braucht es keinen Namen im PDF, die macht das System über die
   Bewerbungs-ID; die Kontaktdaten stehen schon im Formular.
   Entschieden (A): Hinweis im Formular, den Lebenslauf ohne Namen, Foto, Geburtsdatum und Adresse
   hochzuladen. Grenze: Das ist eine Bitte, kein Zwang; das System kann es nicht prüfen.
   Verworfen: PDF erst nach dem Aufdecken (zu wenig Information für die Vorauswahl),
   normaler Lebenslauf ohne Hinweis (Anonymität nur auf dem Bildschirm).
2. Suche und Anonymität:
   Eine Namenssuche, die auch anonyme Bewerbungen findet, würde die Anonymität umgehen.
   Entschieden: Nummer findet jede Bewerbung, Name/E-Mail nur aufgedeckte.
   Begründung (eigener Anwendungsfall): In der anonymen Phase arbeitet man über Stelle + Status +
   Nummer. Den Namen kennt man erst nach dem Aufdecken, z. B. zur Vorbereitung auf das Gespräch,
   dann findet ihn die Suche.

Gebaut (server/routes/admin.js):
1. presentApplication(row): zentrale Stelle für die Anonymität.
   Ohne revealed_at -> nur "Bewerbung #0001", keine Namen, keine E-Mail, kein Telefon.
2. APPLICATION_SELECT: gemeinsamer Teil der Abfragen (Bewerbung + Stelle + Bewerber).
3. GET /api/admin/applications: Liste mit Filtern (Stelle, Status, Suche), 10 pro Seite.
4. GET /api/admin/applications/:id: Detail mit Anhängen, Notizen und Verlauf.
5. GET /api/admin/attachments/:id: Lebenslauf-Download.
Frontend:
6. api/index.js: getApplications, getApplication, attachmentUrl auf den Server umgestellt.
7. Texte an das Konzept angepasst (Applications.jsx, ApplicationDetail.jsx, Apply.jsx).

Erklärungen:
- Anonym heißt: Die Daten verlassen den Server nicht. Nur im Frontend ausblenden reicht nicht,
  weil man die Antwort in den Entwicklertools sehen könnte. Deshalb liefert presentApplication
  in der anonymen Phase first_name, last_name, email, phone gar nicht erst aus.
- Alle Routen geben Bewerbungen nur über presentApplication heraus. Die Regel aus E4 steht an
  einer Stelle und kann in keiner Route vergessen werden (auch nicht später in der Pipeline).
- Filter dynamisch zusammengebaut (conditions/params) wie bei der Stellensuche in B4.
  Werte nur über ? in der Abfrage -> Schutz vor SQL-Injection (Sicherheitstest T09).
- Suche: /^#?\d+$/ erkennt eine Nummer (auch "#0042"). Sonst LIKE '%...%' auf Name + E-Mail,
  aber nur mit "revealed_at IS NOT NULL". || hängt in SQL Texte aneinander.

B7 Etappe 3: Statuswechsel mit Aufdecken, Löschfrist und Bewertung
